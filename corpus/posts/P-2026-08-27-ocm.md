I recently migrated a financial analysis system from R to Java — swap curve bootstrapping, hedge analytics, a loan portfolio with 865,000 contracts. Along the way I found four real bugs in the original code.

I fixed none of them. On purpose.

Here's the trap in every migration: whoever does the rewrite — a developer or an AI — quietly "improves" things. A unit gets normalized here, an edge case handled there. Then the new numbers don't match the old ones, and you can no longer tell which differences are migration errors and which were always there. The migration has silently rewritten history.

So I treated the migration as a measurement, not a rewrite. I call the protocol "Observed & Controlled Migration", and three ideas carry it:

1. An information barrier.
Two AI agents plus a controller. The R-agent reads the original code and describes what it observably does — it never suggests fixes. The Java-agent builds from a neutral, sanitized specification — it never sees a single line of R. The controller sits between them and only compares evidence. If the Java side can't peek at the R side, it can't inherit its habits — or its bugs.

2. Neutral checkpoints.
At every semantic boundary — curve bootstrapped, spread computed, portfolio aggregated — both sides emit identical machine-readable evidence: same fields, same units, same order. Verification means comparing numbers, not reading code. When the sides disagree, the first divergent checkpoint tells you exactly where.

3. Executable preconditions.
Every assumption becomes a runnable check with an ID. "The tenor grid has no gaps" is P08. "Observed spreads fit inside the sweep grid" is P21. When real data violates one, the pipeline doesn't patch it silently — it records a documented finding.

And real data did violate them. The threshold sweep grid turned out ~70x too narrow (a percent-vs-decimal confusion). The backtest triggers entries in percent but prices them in decimal. Two decision rules point in opposite directions. Tenor gaps beyond 30 years quietly corrupt discount factors. All documented, none fixed — because changing production logic is a business decision that deserves a human signature, not a silent edit inside a rewrite.

A few engineering choices I'm fond of: zero external dependencies (a hand-written XLSX reader on the JDK's zip + StAX), IEEE-754 doubles throughout to match R's numeric semantics, and self-tests that verify by inversion — bootstrap the curve, re-price the instruments, check you recover the inputs — so tests survive data changes without hard-coded answers.

What stuck with me: separating observation from correction turns a risky rewrite into an audit. The Java code was the deliverable. The evidence trail was the value.
